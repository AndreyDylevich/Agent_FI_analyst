# Agent_FI_analyst

ИИ-агент финансового анализа российских публичных компаний: находит официальную отчётность,
извлекает данные, считает показатели по реестру, выявляет тревожные сигналы и отправляет отчёт в Telegram.

- Архитектура, методология, источники и статус этапов — [CLAUDE.md](CLAUDE.md).
- Требования к содержанию анализа — [docs/requirements.md](docs/requirements.md).

Плановая проверка источников — раз в 6 часов: 00:00, 06:00, 12:00 и 18:00 UTC
(03:00, 09:00, 15:00 и 21:00 МСК). Сейчас workflow запускает тесты вручную;
мониторинг и расписание подключаются на этапе 7. Команда боту `/report` в планируемой
архитектуре обрабатывается при ближайшем прогоне; ручной запуск GitHub Actions не ждёт расписания.

## Установка

```bash
python3.12 -m venv .venv
.venv/bin/pip install -r requirements.txt
cp .env.example .env   # заполнить ключи
```

Для GigaChat нужен корневой сертификат Минцифры: скачать с https://www.gosuslugi.ru/crt
и положить в `certs/russian_trusted_root_ca.cer`.

## Тесты

```bash
.venv/bin/pytest -q
```

## Служебные команды

```bash
# Поиск организации в ГИР БО (кандидаты на ИНН)
.venv/bin/python -m agent.tools.find_inn "Сегежа Групп"

# Расчёт по уже сохранённым исходным данным (без сети, не изменяет базу)
.venv/bin/python -m agent.tools.calculate MTSS --year 2026 --period H1 --standard IFRS --metric net_debt_to_ebitda

# Рост выручки: H1 сравнивается с H1 прошлого года
.venv/bin/python -m agent.tools.calculate MTSS --year 2026 --period H1 --standard IFRS --metric revenue_yoy

# CAGR по годовой выручке за три интервала: нужны значения за 2022–2025 годы
.venv/bin/python -m agent.tools.calculate MTSS --year 2025 --standard IFRS --metric revenue_cagr_3y

# Оборачиваемость запасов и период оборота в днях (LTM)
.venv/bin/python -m agent.tools.calculate MVID --year 2026 --period H1 --standard IFRS --metric inventory_turnover --metric inventory_days

# ROIC: EBIT LTM, налоговая ставка и средний инвестированный капитал с учётом аренды
.venv/bin/python -m agent.tools.calculate MVID --year 2026 --period H1 --standard IFRS --metric roic

# FCF для акционеров: проценты вне CFO и погашение основной суммы аренды
.venv/bin/python -m agent.tools.calculate MVID --year 2026 --period H1 --standard IFRS --metric fcf_to_equity

# Добавить --save, чтобы сохранить результат и цепочку его источников в SQLite

# Независимая диагностика доступа к ГИР БО (сеть; основная БД и watchlist не меняются)
.venv/bin/python -m agent.tools.check_girbo --output validation/girbo
```

Команда расчёта требует компанию в таблице `companies` и исходные значения в `source_values`.
Она не загружает отчётность. Для РСБУ автоматически используется охват отдельного юрлица;
для МСФО — группы либо сегмента (`--segment`). Отрасль берётся из `watchlist.yaml` или параметра
`--industry`. Без `--metric` рассчитываются все доступные для отрасли и стандарта показатели.

Сейчас реализован 41 показатель: ликвидность, долг, покрытие процентов, CapEx, простой FCF,
конверсия CFO/EBITDA, маржинальность, ROE, ROA, рост выручки год к году, CAGR за 3/5 лет
и оборачиваемость запасов, дебиторской и кредиторской задолженности в оборотах и днях,
инвестированный капитал, эффективная/номинальная ставки налога для ROIC, сам ROIC и FCF для акционеров.
Движок готовит LTM и средние остатки,
сохраняет источники и версии формул, блокирует расчёт при противоречащих данных.
Тесты используют синтетические примеры; сверка с реальной отчётностью пока не выполнена.

Рост год к году сравнивает один тип периода, стандарт, валюту и охват. При базе ≤ 0 он неприменим;
текущая нулевая выручка при положительной базе означает снижение на 100%.
CAGR доступен только для FY и требует полной положительной годовой истории: 4 значения для окна
3 года, 6 значений для окна 5 лет. Пропуски блокируют расчёт. Изменения состава бизнеса
и определения выручки требуют отдельной проверки раскрытий.

Оборачиваемость использует выручку LTM (для запасов и кредиторки — себестоимость LTM)
и средний остаток за тот же скользящий год. При отсутствии начального остатка используется
конечный с пометкой. Срок в днях равен 365 / оборачиваемость; при нулевой оборачиваемости
он не рассчитывается. Показатели применяются только к отраслям с группой `turnover` в конфиге.

ROIC рассчитывается по МСФО для нефинансовых компаний: EBIT LTM × (1 − ставка налога)
/ средний инвестированный капитал. Капитал включает процентный долг и аренду, деньги вычитаются.
Эффективная ставка берётся из налога и прибыли до налогообложения LTM. Если её нельзя использовать,
берётся номинальная из `config/methodology.yaml` на дату конца периода с явной пометкой о допущении.
При конфликте налоговых источников резервная ставка не применяется. Версия и точное значение конфига,
источник ставки и причина её выбора сохраняются с расчётом. Номинальная ставка не учитывает льготы
компании и иностранные сегменты; при смене ставки внутри LTM она не усредняется.

FCF для акционеров по методике проекта = CFO − CapEx − проценты вне CFO − основная сумма аренды.
Для `interest_paid` нужен `source_values.cash_flow_section`: `operating`, `investing` или `financing`.
Проценты внутри CFO повторно не вычитаются. `mixed` без разбивки или неизвестный раздел ненулевого
платежа блокирует расчёт. При разбивке каждый платёж хранится отдельной строкой с разделом,
документом и страницей. Нулевые проценты и нулевое погашение аренды должны быть раскрыты явно.
Классификация учитывается отдельно в каждом периоде LTM. Показатель не определяет допустимые дивиденды.

Схема БД — версия 2. Вызов `agent.db.init_db()` автоматически добавляет поле раздела ОДДС
к базе версии 1, сохраняя историю. Старые строки получают NULL; классификация не угадывается.
Команда расчёта без `--save` может читать старую базу без изменения схемы, но FCF для акционеров
при недостаточной классификации рассчитан не будет.

Для проверки доступности источника из среды GitHub подготовлен ручной workflow
`.github/workflows/check-girbo.yml` («Проверка доступности ГИР БО»). Он проверяет поиск и известные
данные БФО и ссылки-кандидаты PDF по опубликованной годовой версии. Протокол и доступные документы
сохраняются артефактом `girbo-source-check`;
при ошибке источника запуск завершается с кодом 1, протокол сохраняется. Ни секреты, ни Telegram
в этой проверке не используются. Финансовые значения из PDF автоматически не извлекаются и не сверяются.

Локально ГИР БО вернул `Connection refused`. С GitHub получены JSON БФО МТС и М.Видео за 2021–2025 годы;
оригинальные ответы и источники/контрольные суммы сохранены в `tests/fixtures/girbo/`.
PDF пока не скачан, при повторной проверке наблюдались сбои доступа и к JSON. Протоколы и ссылки
на запуски: `docs/validation/girbo_local_access.json` и `docs/validation/girbo_github_access.json`.
PDF М.Видео за 2025 год удалось прочитать через веб-инструмент; по тексту подтверждены единица
и выбранные строки. В `tests/fixtures/girbo/mvideo_2025_reference.json` сохранена независимая сверка
9 коэффициентов и 2 денежных показателей; протокол движка — `docs/validation/mvideo_rsbu_2025_check.json`.
Скриншоты PDF не получены; это выборочная текстовая сверка, не аудит всей отчётности.

## Импорт сохранённой РСБУ

```bash
.venv/bin/python -m agent.tools.import_girbo tests/fixtures/girbo/mvideo_bfo_metadata.json \
  --db validation/mvideo_demo.db --ticker MVID --expected-inn 7707602010 --year 2025 \
  --source-url https://bo.nalog.gov.ru/nbo/organizations/5155604/bfo/ \
  --unit 'тыс. руб.' --unit-source 'https://bo.nalog.gov.ru/download/bfo/pdf/57656029#page=1' \
  --confirm-unit --industry retail --metric current_ratio --metric net_debt \
  --output validation/mvideo_demo.json
```

Команда не обращается к сети и не меняет `watchlist.yaml`. Выбор ИНН здесь относится к явно
указанной проверочной БД; подтверждение юрлиц в списке наблюдения остаётся отдельным действием.
Нужны подтверждённая единица и её источник; для контроля файла можно передать `--sha256`.
Сохраняются исходный знак, нормализованная сумма, JSON-путь, контрольная сумма и контекст единицы.
Пропуски не заменяются нулями. Повторный импорт не дублирует источники; расхождения между документами
помечаются с обеих сторон и блокируют соответствующие расчёты. Разбор налогового дохода и расхода разделён.

Расчётный этап 2 завершён. Этап 3 не начат: перед мониторингом ждём дополнения пользователя
и выполняем ранее запланированную проверку подключения Telegram.
