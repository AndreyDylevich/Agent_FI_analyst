# Agent_FI_analyst

ИИ-агент финансового анализа российских публичных компаний: находит официальную отчётность,
извлекает данные, считает показатели по реестру, выявляет тревожные сигналы и отправляет отчёт в Telegram.

- Архитектура, методология, источники и статус этапов — [CLAUDE.md](CLAUDE.md).
- Требования к содержанию анализа — [docs/requirements.md](docs/requirements.md).

ИИ извлекает и интерпретирует данные; Python рассчитывает показатели и выполняет формальные проверки.
Обязательные проверки извлечения, бухгалтерских тождеств, связей между формами, методологии,
сопоставимости и выводов ИИ описаны в разделах 9–10 требований, включая IFRS 16/17/18.
Реализованы арифметические проверки кодированных форм РСБУ через `agent/checks/validate.py`
и API проверки сопоставимости. В новом пути `extract_ifrs` включён строгий режим движка:
для сравнений, LTM и средних остатков нужны подтверждённые учётная база, периметр и методика
со ссылкой на раскрытия. Старый CLI `calculate` остаётся режимом диагностического просмотра.
Полный контур проверок МСФО — этап 4,
проверка структурированных выводов ИИ — этап 6. Совпадение чисел не доказывает правильность вывода.

Плановая проверка источников — раз в 6 часов: 00:00, 06:00, 12:00 и 18:00 UTC
(03:00, 09:00, 15:00 и 21:00 МСК). Сейчас workflow запускает тесты вручную;
мониторинг и расписание подключаются на этапе 7. Команда боту `/report` в планируемой
архитектуре обрабатывается при ближайшем прогоне; ручной запуск GitHub Actions не ждёт расписания.

## Установка

```bash
python3.12 -m venv .venv
.venv/bin/pip install -r requirements.txt
cp .env.example .env   # заполнить ключи
```

Для GigaChat используется публичный корневой сертификат Минцифры:
`certs/russian_trusted_root_ca.cer`, источник и SHA256 — в `certs/manifest.json`.
Сертификат получен с официального адреса по HTTPS с проверкой TLS; системное хранилище не меняется.
SDK проверяет TLS, отключение проверки не используется. Ключ локально читается из `.env`
без замены уже заданных переменных окружения; в Actions — из `GIGACHAT_KEY`.

## Мониторинг IR (этап 3)

```bash
# Первый успешный запуск фиксирует существующие PDF без загрузки архива.
# Последующие запуски загружают новые ссылки и повторяют неудачные загрузки.
.venv/bin/python -m agent.tools.monitor_ir --output validation/monitor/ir.json

# Одна компания и отдельная тестовая база
.venv/bin/python -m agent.tools.monitor_ir --ticker SGZH --db validation/demo.db --files validation/pdf --output validation/demo.json

# Явный аудит замены PDF по прежнему URL, включая архив базовой линии
.venv/bin/python -m agent.tools.monitor_ir --recheck-known --max-downloads 20 --output validation/audit.json

# Контролируемое воспроизведение новых ссылок на реальных страницах, в НОВОМ каталоге
.venv/bin/python -m agent.tools.check_ir --output validation/ir-check

# Проверка авторизации Telegram и права публикации, без отправки сообщений
# TG_TOKEN и TG_CHAT_ID должны быть в окружении (GitHub workflow берёт их из Secrets).
.venv/bin/python -m agent.tools.check_telegram --output validation/telegram.json
```

Ручной workflow **«Мониторинг IR вручную»** сохраняет очередь, источники и версии документов
в `data/agent.db` и коммитит БД в `main`, в том числе после частичного сбоя источника.
Есть выбор тикера и аудит прежних URL. Параллельные запуски, меняющие БД, идут последовательно.
HTML проверяется при каждом прогоне; первая успешная базовая линия создаётся отдельно для каждой
страницы. Недоступная страница не считается пустым успешным источником.

PDF загружаются потоково с ограничением 20 МБ и 60 секунд чтения. Проверяются HTTPS-хосты
и каждое перенаправление, тип ответа, сигнатура и структура PDF; поддерживается AES с пустым паролем.
Капчи не обходятся. SHA256 одинаковых файлов под разными URL предотвращает повтор документа
одной компании; разные версии сохраняются раздельно. Новая подпись известной ссылки ставит её
в очередь повторно. **Тихая замена байтов по прежнему URL без изменения подписи проверяется через
`--recheck-known`**, а не обычным сравнением списка ссылок. Аудит использует ETag/Last-Modified,
когда есть подтверждённый локальный файл, и сравнивает SHA256; при отсутствии HTTP-валидаторов
нужна повторная загрузка. Лимит оставляет необработанные задачи для следующего запуска;
ненулевой код завершения также означает ошибки или отложенные задачи, а не потерю очереди.

Классификатор различает отчётность, пресс-релиз, презентацию, годовой отчёт и прочие документы.
Используются подпись и текст первой страницы; папка `/IFRS/` не доказывает стандарт.
Сохраняются основание, версия правила, фрагмент текста и признак ручной проверки.
Неизвестный/конфликтующий стандарт или период не угадывается. Отдельный квартал Q2/Q3/Q4
не подменяется накопленным H1/9M/FY. При пустом тексте первой страницы у источников `link_text`
классификация возможна по подписи; для `pdf_first_page` остаётся неопределённость.
Это классификация, а не подтверждение финансовых значений или применённой учётной политики.

Диагностика **«Проверка IR-источников»** не меняет основную БД: скрывает несколько реальных ссылок
в первом снимке и возвращает их во втором, скачивает документы, затем проверяет отсутствие
повторной загрузки при том же снимке. Это воспроизведение события, а не новая публикация эмитента.
Отдельная **«Проверка подключения Telegram»** проверяет только getMe/getChat/getChatMember.
Протокол не содержит токена, ID, названия или имени канала/бота; сообщений не отправляет.

В Actions PDF и протокол ручного мониторинга сохраняются артефактом `ir-monitor-result` на 30 дней;
диагностика — `ir-source-check` на 14 дней. В git хранятся SQLite и контрольные суммы, не PDF.
Путь в БД сам по себе не гарантирует наличие файла в новом runner: для следующего этапа нужен
артефакт или повторная загрузка с проверкой SHA256. Локально файлы остаются в `data/documents/`.
Историческая загрузка за 3–5 лет, извлечение финансовых данных и отправка отчётов — следующие этапы.
Расписание раз в 6 часов включается на этапе 7.

Проверенные запуски и ограничения: [протокол этапа 3](docs/validation/stage3_check.md).

## Извлечение МСФО (этап 4, в работе)

`agent.extract.llm` подключает согласованную модель GigaChat-2-Max через проверенный TLS.
Ручной workflow «Проверка GigaChat и TLS» проверяет доступность модели и короткий JSON-ответ;
токены/ключи авторизации в протокол не попадают. В модель передаётся текст выбранных страниц,
а не PDF-файл целиком. Страницы форм и тем примечаний выбираются по заголовкам.

```bash
# Пример для уже скачанного официального PDF МТС 1П2026, отдельной БД и нового каталога ответов
.venv/bin/python -m agent.tools.extract_ifrs /path/to/report.pdf \
  --ticker MTSS --year 2026 --period H1 --db validation/ifrs_demo.db \
  --source-url https://static.mts.ru/mts_rf/contents/10677/mts_ifrs_cons_cond_i_fs_q2_26_2608_final.pdf \
  --output validation/ifrs_demo --sections balance \
  --item total_assets --item non_current_assets --item current_assets \
  --item equity_total --item non_current_liabilities --item current_liabilities \
  --item total_equity_and_liabilities --metric current_ratio
```

Ответ модели строго проверяется: компания, явное указание МСФО, групповой охват, RUB,
отчётное окно, физические страницы, адреса строк и скопированные Python цитаты, числа со знаками,
год колонки и канонические статьи. Статусы проверки и нормализованные значения модель не задаёт.
Формат чисел задаётся явно: `376,772` может означать тысячи; неоднозначное представление
не переводится молча в дробь. Все преобразования единиц и расчёты делает Python через Decimal.

Для балансовых остатков модель возвращает AT_DATE и конкретную дату; Python определяет календарную
метку. Для потоков нужны обе границы накопленного периода. Год без длительности не подтверждает
окно отчётности. Совпадение текста заголовка/года **не доказывает** правильный выбор пространственной
колонки — для эталона используется отдельная сверка с вручную прочитанными значениями PDF.

Сейчас реализованы тождества баланса, частей активов/пассива, валовой прибыли и полного состава
кредитов/займов при наличии всех входов. Для округлённых МСФО допуск — одна исходная единица,
с сохранением абсолютной разницы/допуска в рублях. Неполные входы не считаются нулями.
Ошибки структуры/источников вызывают один повтор; обе попытки и ошибки сохраняются.
Повторное арифметическое расхождение сохраняется со статусом расхождения, без автоматической
перезаписи старых источников. Цитата/формальное равенство сами по себе не являются аудитом статьи.
Если повтор удалил подтверждённую строку, испортил ссылку/число или завершился ошибкой провайдера,
сохраняется полный первоначальный набор с расхождением. Исправлять числа ради равенства запрещено.
Диагностика может подтвердить точное соответствие заранее сверенной ошибке источника: при этом
`extraction_ok=false`, спорные строки сохраняют статус `расхождение` и блокируются в расчётах.

Непрочитанные страницы явно отмечаются. Для `--ocr` нужны Poppler (`pdftoppm`) и Tesseract
с языками rus+eng; по умолчанию лимит 20 OCR-страниц (`--max-ocr-pages`). OCR происходит локально при разрешении
320dpi, с сохранением межколоночных пробелов. Его строки остаются непроверенными для
автоматических расчётов; диагностическая сверка эталона сама по себе не повышает статусы. В автоматический расчёт этой команды
допускаются только проверенные строки; конфликтующие сохраняются и блокируют зависимые расчёты.

Контекст, исходная запись числа, формат, масштаб, цитата, страница, модель/версия промпта и SHA256
сохраняются в SQLite/протоколе. В этой команде БД задаётся явно; watchlist, основная БД мониторинга
и Telegram автоматически не меняются. Непустой повторно используемый каталог вывода запрещает
случайную перезапись истории ответов.

Этап 4 ещё не завершён: полные сверки ОДДС, изменений капитала и примечаний между формами,
проверки учётной базы/периметра, эталоны всех трёх компаний и загрузка истории за 3–5 лет
остаются в плане. Успех отдельного извлечения не означает готовности полного отчёта к отправке.

Команда расчёта требует компанию в таблице `companies` и исходные значения в `source_values`.
Она не загружает отчётность. Для РСБУ автоматически используется охват отдельного юрлица;
для МСФО — группы либо сегмента (`--segment`). Отрасль берётся из `watchlist.yaml` или параметра
`--industry`. Без `--metric` рассчитываются все доступные для отрасли и стандарта показатели.

Сейчас реализован 41 показатель: ликвидность, долг, покрытие процентов, CapEx, простой FCF,
конверсия CFO/EBITDA, маржинальность, ROE, ROA, рост выручки год к году, CAGR за 3/5 лет
и оборачиваемость запасов, дебиторской и кредиторской задолженности в оборотах и днях,
инвестированный капитал, эффективная/номинальная ставки налога для ROIC, сам ROIC и FCF для акционеров.
Движок готовит LTM и средние остатки,
сохраняет источники и версии формул, блокирует расчёт при противоречащих данных.
Тесты используют синтетические примеры и сохранённые реальные ответы. Выборочные приёмки
РСБУ и МСФО описаны ниже; они не означают проверки всех 41 показателя на реальной отчётности.

Рост год к году сравнивает один тип периода, стандарт, валюту и охват. При базе ≤ 0 он неприменим;
текущая нулевая выручка при положительной базе означает снижение на 100%.
CAGR доступен только для FY и требует полной положительной годовой истории: 4 значения для окна
3 года, 6 значений для окна 5 лет. Пропуски блокируют расчёт. Изменения состава бизнеса
и определения выручки требуют отдельной проверки раскрытий.

Оборачиваемость использует выручку LTM (для запасов и кредиторки — себестоимость LTM)
и средний остаток за тот же скользящий год. При отсутствии начального остатка используется
конечный с пометкой. Срок в днях равен 365 / оборачиваемость; при нулевой оборачиваемости
он не рассчитывается. Показатели применяются только к отраслям с группой `turnover` в конфиге.

ROIC рассчитывается по МСФО для нефинансовых компаний: EBIT LTM × (1 − ставка налога)
/ средний инвестированный капитал. Капитал включает процентный долг и аренду, деньги вычитаются.
Эффективная ставка берётся из налога и прибыли до налогообложения LTM. Если её нельзя использовать,
берётся номинальная из `config/methodology.yaml` на дату конца периода с явной пометкой о допущении.
При конфликте налоговых источников резервная ставка не применяется. Версия и точное значение конфига,
источник ставки и причина её выбора сохраняются с расчётом. Номинальная ставка не учитывает льготы
компании и иностранные сегменты; при смене ставки внутри LTM она не усредняется.

FCF для акционеров по методике проекта = CFO − CapEx − проценты вне CFO − основная сумма аренды.
Для `interest_paid` нужен `source_values.cash_flow_section`: `operating`, `investing` или `financing`.
Проценты внутри CFO повторно не вычитаются. `mixed` без разбивки или неизвестный раздел ненулевого
платежа блокирует расчёт. При разбивке каждый платёж хранится отдельной строкой с разделом,
документом и страницей. Нулевые проценты и нулевое погашение аренды должны быть раскрыты явно.
Классификация учитывается отдельно в каждом периоде LTM. Показатель не определяет допустимые дивиденды.

Схема БД — версия 3. Вызов `agent.db.init_db()` автоматически добавляет поле раздела ОДДС
к базе версии 1 и таблицы мониторинга к версиям 1/2, сохраняя историю. Старые строки раздела
ОДДС получают NULL; классификация не угадывается.
Команда расчёта без `--save` может читать старую базу без изменения схемы, но FCF для акционеров
при недостаточной классификации рассчитан не будет.

### Полный мост движения долга

Версия 10 проверок сверяет полный раскрытый мост долга МТС за 1П2026:
отдельно облигации, кредиты/прочие займы и их общий результат. Структура привязана к SHA256
и физическим страницам 18/19 в `config/ifrs_debt_bridges.json`. Все выпуски, выплаты,
курсовые/прочие движения и деконсолидация учитываются отдельно с исходными знаками.
Взаимно компенсирующиеся ошибки компонентных мостов блокируют общий результат.
Четыре связи с ОДДС отдельно сверяют выпуски/погашения облигаций и привлечение/погашение кредитов.

```bash
# Свежая проверка по независимому визуальному эталону 21 суммы

  --output validation/mts_debt_movement_fresh
```

по аренде за оба полугодия. Причины и адреса раскрытий сохранены в `unavailable_bridges`.
Поступления активов права пользования не подменяют новые обязательства по аренде;
отдельные операции БИК и платежи не замыкают полный мост. Пропуски остаются пропусками.
