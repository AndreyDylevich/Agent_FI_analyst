# Agent_FI_analyst — ИИ-агент финансового анализа российских публичных компаний

Прочитай этот файл целиком перед любой задачей.
- `docs/requirements.md` — требования пользователя к содержанию анализа (что считать, как интерпретировать,
  формат отчёта). Это главный документ по СОДЕРЖАНИЮ.
- Этот файл — решения по архитектуре, методологии, источникам и текущему состоянию проекта.
Если задача противоречит одному из них — спроси, прежде чем делать.

## 1. Цель

Агент:
1. отслеживает выход отчётности компаний из списка наблюдения (раз в 6 часов) и работает по запросу пользователя;
2. находит и скачивает официальную отчётность;
3. извлекает и нормализует данные (МСФО — основа; РСБУ — для отдельных юрлиц);
4. определяет отрасль и бизнес-модель компании и выбирает набор показателей;
5. считает общие и отраслевые показатели, анализирует динамику за 3–5 лет;
6. сравнивает компанию с российскими публичными аналогами;
7. объясняет результаты с помощью ИИ и выявляет риски — без инвестиционных рекомендаций;
8. формирует отчёт с проверяемыми расчётами и ссылками на первоисточники и отправляет его в Telegram.

Исходный фокус проекта — долговая устойчивость и тревожные изменения — остаётся ядром:
алерты по долгу, ликвидности и покрытию процентов обязательны для всех нефинансовых компаний.

Пользователь — финансовый аналитик. Ему важна проверяемость: каждая цифра ведёт к источнику
(документ + страница), каждая формула видна.

## 2. Принятые решения (не менять без согласования)

- **Язык:** Python 3.11+.
- **Запуск:** GitHub Actions; по исходному плану репозиторий приватный.
  Проверка GitHub API 21.11.2026 показала, что фактически репозиторий публичный; видимость не менялась.
  - По событию: раз в 6 часов (`cron: "0 */6 * * *"`, UTC) проверка новых отчётов.
  - Плановые проверки: 00:00, 06:00, 12:00 и 18:00 UTC (03:00, 09:00, 15:00 и 21:00 МСК).
  - По запросу: `workflow_dispatch` с параметром «тикер», а также команда боту `/report <тикер>`
    (обрабатывается при ближайшем прогоне; плановый интервал — 6 часов).
  - Локально — тот же код, ключи из `.env`.
- **Хранилище:** SQLite `data/agent.db`; после прогона в Actions агент коммитит файл обратно
  (`permissions: contents: write`).
- **LLM:** GigaChat (тариф Freemium для физлиц), `GigaChat-2-Max` для извлечения и интерпретации.
  В модель отправляется ТЕКСТ нужных страниц, а не весь PDF. Провайдер спрятан за интерфейсом
  (`extract(pages) -> JSON`, `interpret(facts) -> text`) — его можно заменить.
- **Парсер таблиц не пишем.** Извлечение из МСФО — через LLM + обязательные проверки.
- **LLM ничего не считает.** Все показатели считает Python через реестр показателей (раздел 6).
- **Доставка:** Telegram (канал AI_analyst). Сообщение — кратко: ключевые цифры, изменения, тревожные сигналы.
  Полный отчёт (структура — `docs/requirements.md`, раздел 11) — файлом; плюс Excel с исходными значениями,
  источниками и формулами; плюс PDF исходной отчётности. Формат файла полного отчёта решаем на этапе 6.
- **Секреты** (GitHub Secrets и локальный `.env`): `GIGACHAT_KEY`, `TG_TOKEN`, `TG_CHAT_ID`.

### Новые файлы
Первый запуск по компании — «базовая линия»: текущие PDF записываются как виденные без скачивания.
Дальше скачиваются только новые (сравнение по URL и sha256). Исторические отчёты для динамики
за 3–5 лет загружаются отдельной разовой командой (backfill).

Этап 3 реализован через `agent.tools.monitor_ir`: состояние инициализации хранится отдельно
для каждой IR-страницы; сбой не создаёт базовую линию. Неудачные загрузки остаются в очереди.
Подпись известного URL изменилась — повторная проверка PDF; тихая замена без изменения подписи
проверяется явным `--recheck-known`. Без аудита архив базовой линии не скачивается.
Аудит поддерживает условные запросы ETag/Last-Modified при наличии проверенного локального файла.
Совпавший SHA256 одной компании — повтор документа, новый SHA256 — отдельная версия;
все адреса и связи с документами сохраняются. Непонятная классификация остаётся с needs_review.

Проверка 21.11.2026 из GitHub подтвердила все три страницы: МТС — 127 PDF-ссылок,
М.Видео — 21, Сегежа — 74. В отдельной диагностике скачаны 7 реальных PDF: МСФО/РСБУ МТС
и М.Видео, МСФО Сегежи, её пресс-релиз и короткая выдержка без явного стандарта.
Последняя оставлена `other` с ручной проверкой. У трёх PDF титульная страница без извлекаемого
текста: тип задан по подписи ссылки, а не по содержимому. Финансовые значения не проверялись.
Подробности и ссылки на запуски — `docs/validation/stage3_check.md`.

## 4. Компании и отрасли

Список наблюдения — `config/watchlist.yaml`. ИНН не вписывать по памяти — искать через ГИР БО
и подтверждать у пользователя.

| Компания | Отрасль (из справочника) | Особенности |
|---|---|---|
| МТС | Телекоммуникации; сегменты: финтех (МТС Банк), медиа, экосистема | Банк консолидирован: банковские активы/обязательства искажают ликвидность и долг. Долг — корпоративные кредиты, займы, облигации; показатели без банка — по сегментной информации, если позволяет; иначе явная пометка |
| М.Видео | Розничная торговля (электроника), онлайн-продажи | Крупная аренда (МСФО 16) — метрики с арендой и без. Раскрывает GMV — не приравнивать к выручке |
| Сегежа | Лесная и целлюлозно-бумажная промышленность (добавить в справочник как 21-ю категорию) | Высокая долговая нагрузка; при EBITDA ≤ 0 Долг/EBITDA не считать — пометка |

### Определение отрасли
1. Автоматическое предложение: ОКВЭД (ГИР БО) + LLM по описанию деятельности и примечанию «Сегментная информация».
2. Результат: отрасль, сегменты, бизнес-модель, уверенность, обоснование (со ссылкой на документ).
3. Пользователь подтверждает — значение фиксируется в `watchlist.yaml` и имеет приоритет над автоматическим.
4. Пересмотр — при изменении структуры сегментов в новой отчётности (агент сообщает об этом).
Конгломераты: основная отрасль + сегменты; отраслевые показатели — по сегментам, если есть сегментная отчётность.

## 5. Модель данных

### Документы
URL, sha256, название, тип (МСФО / РСБУ / пресс-релиз / презентация / годовой отчёт / прочее), стандарт,
период, дата публикации, дата обнаружения, статус обработки.

### Исходные значения (из отчётности и операционных раскрытий)
Для каждого значения: компания; показатель (канонический id из `config/line_items.yaml`
или id операционного показателя); исходное наименование статьи как в отчёте; значение (точно, TEXT);
единица (руб. / тыс. руб. / млн руб. или натуральная: тыс. т, млн абонентов, шт.); нормализованное
значение (руб. для денежных); валюта; период (дата начала, дата окончания, тип FY/Q1/H1/9M; для балансовых — дата);
стандарт (МСФО / РСБУ / операционные данные); охват (группа / юрлицо / сегмент + название сегмента);
документ; источник (`girbo` / `ir_page` / `press_release` / `moex`); страница или раздел;
кем извлечено (`girbo` / `gigachat` / `manual`); статус проверки
(`не_проверено` / `проверено_авто` / `расхождение` / `проверено_вручную`); признак пересчитанных
сравнительных данных; признак разовой статьи (с кратким обоснованием из отчёта).
Для денежных платежей — `cash_flow_section`: `operating`, `investing`, `financing`, `mixed` или NULL
(раздел неизвестен). `mixed` — итог по нескольким разделам без разбивки.
Схема SQLite — версия 3; `init_db()` добавляет поле раздела ОДДС к версии 1 и таблицы мониторинга
к версиям 1/2, сохраняя значения, историю и связи расчётов. `ir_pages` хранит состояние источника,
`ir_links` — очередь и HTTP-валидаторы, `ir_observations` — связи ссылок с версиями документов,
`document_classifications` — версию и основание классификации. PDF — локально или в артефакте
Actions; SQLite хранит путь и SHA256. В новом runner файл восстанавливается из артефакта
или повторно скачивается с проверкой SHA256; срок хранения артефактов описан в README.

### Рассчитанные показатели
id показателя из реестра, версия формулы, период, значение, единица, ссылки на использованные исходные значения,
статус (`рассчитан` / `неприменим` + причина / `недостаточно_данных` + каких), дата расчёта.

### Прочее
Рыночные данные (дата, цена, количество акций, капитализация, источник); отрасль и сегменты компании;
тревожные сигналы.

### Правила точности
- `Decimal` в коде, TEXT в SQLite. Никакого округления при хранении и расчёте.
- Округление только при выводе: коэффициенты — 2 знака, суммы — млн руб. с 1 знаком.
- Отсутствующее значение — `None`, НИКОГДА не 0. Не «дополнять» оценками без явной пометки.
- Исходные значения и расчётные показатели хранятся раздельно.
- Не смешивать МСФО и РСБУ в одном временном ряду без явного предупреждения.
- Противоречащие друг другу данные: не выбирать произвольно — показать расхождение и какой источник взят и почему.

## 6. Реестр показателей (`docs/requirements.md`, раздел 14)

Показатели НЕ зашиваются в условия. Каталог `agent/metrics/`:
- `registry.py` — описание показателя `MetricDef`: id, название, отрасль (`common` или id отрасли), группа,
  формула текстом, входные данные (канонические id), единица, правило периода (на дату / поток / LTM / средний остаток),
  правило при отсутствии данных, экономический смысл, ограничения применимости, условие применимости, версия;
  и функция расчёта, возвращающая значение + использованные входы + статус.
  Для исторических сравнений: `input_items` (псевдоним входа → канонический id),
  `input_year_offsets` (сдвиг года входа) и `period_kinds` (допустимые периоды результата).
  Для явных допущений: `parameter_inputs`, `input_units`; резервный показатель — `input_fallbacks`.
  Для корректировок по классификации ОДДС: `input_cash_flow_sections` задаёт разделы включаемых платежей.
  Значение и версия конфига сохраняются в примечаниях расчёта; допущение не создаёт строку отчётности.
- `common/` — growth, profitability, cash_flow, leverage, liquidity, turnover, market.
- `industries/` — telecom, retail, forestry (сейчас); остальные отрасли — по мере добавления компаний.
- `config/industries.yaml` — справочник отраслей (20 из требований + лесная и ЦБП): id, название, признаки для
  определения (ОКВЭД, ключевые слова), применимые группы общих показателей, исключения
  (например, для банков не считать Чистый долг/EBITDA и EV/EBITDA), отраслевые показатели.
- `config/line_items.yaml` — канонические статьи: id → синонимы в МСФО (рус./англ.), коды РСБУ.
Добавление показателя или отрасли = новая функция + запись в конфиг, без переписывания системы.
Общие и отраслевые показатели разделены.

## 7. Методология — зафиксированные определения

Если у показателя есть разные подходы — используется указанный здесь, последовательно.
Изменение определения = новая версия формулы в реестре.

### Периоды
- Балансовые показатели — на дату; потоковые — за период. Не сравнивать квартал с годом.
- **LTM** для промежуточной отчётности: LTM = год(t−1) + с начала года(t) − с начала года(t−1).
- Сравнение промежуточных периодов — с аналогичным периодом прошлого года (сезонность).
- **Средний остаток** = (начало периода + конец периода) / 2; если начала нет — расчёт по концу с пометкой.
- **CAGR** = (V_конец / V_начало)^(1/n) − 1 — только при положительных значениях и сопоставимом стандарте.
  Реализованы отдельные окна выручки 3 и 5 лет, только FY. Для контроля полноты требуются
  все 4/6 последовательных годовых значений; окно при пропусках не сокращается.
  Промежуточные значения подтверждают полноту/положительность истории, формула использует крайние.
  Дробная степень вычисляется через Decimal с точностью его контекста, без float и округления для вывода.

### Долг и денежные средства (МСФО)
- **Долг** = кредиты и займы + облигации (долгосрочная и краткосрочная части).
- **Аренда** (МСФО 16) хранится отдельно; долговые метрики — в двух вариантах: без аренды и с арендой.
- **Чистый долг** = Долг − денежные средства и эквиваленты (краткосрочные депозиты — отдельно, в базу не входят).

### Результаты
- **EBITDA** = операционная прибыль + амортизация (ОС, НМА, права пользования) + обесценение внеоборотных
  активов, если оно отражено в операционной прибыли и раскрыто. Источник амортизации — ОДДС или примечания.
  «Скорректированная EBITDA» компании хранится отдельно и в базовых расчётах не используется.
- **EBIT** = операционная прибыль.
- **Проценты:** процентные расходы (ОПУ/примечания) и проценты уплаченные (ОДДС) — хранить оба
  (расходятся из-за капитализации по МСФО (IAS) 23). Покрытие считать по обоим.

### Денежные потоки
- **CapEx** = приобретение ОС + приобретение НМА (ОДДС).
- **FCF простой** = CFO − CapEx.
- **FCF для акционеров** = CFO − CapEx − проценты уплаченные (если классифицированы вне CFO)
  − погашение основной суммы аренды. В отчёте указывать, какой вариант.
  Реализован `fcf_to_equity` для нефинансовых компаний по МСФО. Проценты внутри CFO не вычитаются
  повторно; отдельные платежи вне CFO учитываются. Процентная часть аренды включается в уплаченные
  проценты, основная сумма — отдельной статьёй. Неизвестный раздел процентов или mixed без разбивки
  блокирует расчёт; раскрытый нулевой платёж допустим без раздела. Отсутствующая аренда не заменяется нулём.
  При разбивке по разделам нужны согласованные компоненты одного документа либо одинаковая полная
  разбивка в подтверждающих документах; итог и части не складываются. В LTM классификация применяется
  к каждому исходному FY/YTD до сложения потоков. Исходная сумма процентов и её источник сохраняются,
  даже если корректировка равна нулю. Показатель не учитывает погашение/привлечение кредитов
  и не равен сумме, доступной для дивидендов.
- **Конверсия в деньги** = CFO / EBITDA.

### Рентабельность
- **ROE** = чистая прибыль акционерам материнской компании (LTM) / средний капитал акционеров материнской компании.
  При отрицательном капитале — не рассчитывать.
- **ROA** = чистая прибыль (LTM) / средние активы.
- **ROIC** = EBIT × (1 − ставка налога) / средний инвестированный капитал;
  инвестированный капитал = капитал + долг + аренда − денежные средства;
  ставка — эффективная, если определяется, иначе номинальная из конфига (с 2025 года — 25%).
  Эффективная ставка = расход по налогу LTM / прибыль до налогообложения LTM; используется
  при положительной прибыли до налога и значении 0–100%. Нулевой расход должен быть раскрыт явно.
  При отсутствии данных, убытке до налога или ставке вне диапазона — номинальная с пометкой;
  при противоречащих налоговых источниках расчёт блокируется, резерв не используется.
  `config/methodology.yaml`: 20% для 2020–2024 годов, 25% с 2025 года; источники ФНС указаны в конфиге.
  Ставка для допущения берётся на дату окончания периода, без усреднения при смене ставки внутри LTM;
  льготы конкретной компании и иностранные сегменты не учтены — это явно указывается в результате.
  Инвестированный капитал сначала считается в полном составе на обе даты LTM, затем усредняется.
  Если начала нет целиком — конец с пометкой; неполный состав на начало не смешивается с полным на конец.
  При инвестированном капитале ≤ 0 на любой границе ROIC неприменим; отрицательный EBIT сохраняет знак ROIC.
  Налоговый доход нельзя извлекать как положительный расход `income_tax`.

### Оборачиваемость
Выручка (для запасов и кредиторки — себестоимость) LTM / средний остаток; в днях = 365 / оборачиваемость.
Средний остаток берётся на начало и конец именно LTM, не текущего промежуточного периода.
При отсутствии начала используется конец с пометкой; конфликт источников не считается отсутствием.
Отрицательный остаток на любой границе блокирует расчёт; нулевой начальный остаток допустим,
если среднее положительно. При нулевом потоке обороты равны нулю, срок в днях не определяется.
Зависимость от уже рассчитанного коэффициента LTM используется напрямую, без суммирования коэффициентов.

### Рыночные мультипликаторы
- Капитализация = Σ (цена × количество акций в обращении) по категориям акций, на конкретную дату (дату указывать).
- EV = капитализация + чистый долг + неконтролирующие доли (вариант с арендой — + аренда).
- Не интерпретировать P/E при отрицательной прибыли; EV/EBITDA и Чистый долг/EBITDA неприменимы к банкам и финансовым компаниям.

### РСБУ (коды по Приказу Минфина №66н) — для отдельных юрлиц
Текущая ликвидность 1200/1500; быстрая (1230+1240+1250)/1500; абсолютная (1240+1250)/1500;
долг 1410+1510; чистый долг 1410+1510−1250; долг/капитал (1410+1510)/1300 (при 1300 ≤ 0 — пометка);
доля краткосрочного долга 1510/(1410+1510); покрытие процентов (2300+2330)/2330;
денежные средства/краткосрочный долг 1250/1510; автономия 1300/1700.
EBITDA по РСБУ не считаем (нет амортизации в основных формах). В отчёте указывать: «отчётность юрлица, не группы».

### Банки
Нормативы достаточности капитала — только из регуляторных данных (Н1.0 и т.д.), не по упрощённой формуле.

## 8. Проверки

Обязательная спецификация — `docs/requirements.md`, разделы 9–10 (дополнения пользователя
21.11.2026). ИИ извлекает и интерпретирует; Python считает и выполняет формальные проверки.
Проверка арифметики не доказывает правильность извлечения или экономического вывода.

### После извлечения
1. Баланс: активы = капитал + обязательства (РСБУ — точно; МСФО — допуск в единицу округления отчёта).
2. Суммы строк раздела = итог раздела.
3. Сравнительные данные сверяются с историей. Расхождение сохраняется; «пересчитано компанией»
   ставится только при подтверждающем раскрытии, без молчаливой перезаписи.
4. Единицы и период согласованы.
5. Неудачная проверка: один повторный запрос к LLM; не сошлось снова — статус `расхождение`,
   затронутые входы и зависимые расчёты блокируются; отчёт содержит пометку «требует ручной проверки».
6. Нужны сверки между балансом, ОПУ, ОДДС, изменениями капитала и примечаниями.
   Полный мост включает валютные, неденежные изменения и изменения периметра. Разные определения
   денег/долга/прибыли не приравниваются. Неполная сверка — «недостаточно данных», не успех.
7. Сопоставимость включает базу учётной политики, периметр и версию методики. Переходы IFRS 17/18
   и пересчёты требуют раскрытий; календарной даты для признания сопоставимости недостаточно.

`agent/checks/validate.py`: `reconcile()` проверяет тождества с явным допуском, пропусками
и конфликтующими входами; используется в кодированных формах РСБУ. `compare_periods()` проверяет
контекст пары YoY: компания/статья, стандарт, охват/сегмент, валюта/единица, календарное окно,
учётная база, периметр и методика. В `Engine` добавлен строгий режим сопоставимости, включённый в `extract_ifrs`: для одного
входа разных периодов нужны подтверждённые учётная база, периметр, определение и источник.
Без этого YoY/CAGR/LTM/средние остатки блокируются, включая зависимые расчёты. Старый CLI
`calculate` остаётся диагностическим просмотром без этой приёмки. Полного контура МСФО пока нет.

### Интерпретация ИИ (`docs/requirements.md`, разделы 8 и 9.6; реализация — этап 6)
- В модель передаются только рассчитанные показатели и извлечённые факты с периодами.
- Тезисы структурированы: факт/гипотеза, ссылки на факты/расчёты, период, ограничения и контрсигналы.
  Python проверяет числа в их контексте, направления динамики и обязательное отражение рисков;
  совпадения числа с произвольной цифрой в документе недостаточно. Числа подставляет форматтер Python.
- Рост выручки/прибыли при падении CFO и опережающем росте дебиторки требует оговорки
  о возможном снижении качества прибыли, а не общего вывода об укреплении состояния.
  Сигнал не доказывает причину: она подтверждается раскрытием либо обозначается гипотезой.
- Не прошедший проверку тезис перегенерируется один раз, затем заменяется проверенным шаблоном.
  Формальные проверки не гарантируют истинность причинных выводов свободного текста.
- Запрещено: инвестиционные рекомендации, выводы по одному коэффициенту, утверждения без данных.
  Факты и предположения разделяются явно.

## 9. Тревожные сигналы (стартовые пороги, настраиваются в конфиге)

- Чистый долг / EBITDA LTM > 3,0x или рост > 1,0x год к году.
- EBITDA / проценты < 2,0x (критично < 1,0x).
- Текущая ликвидность < 1,0; денежные средства / краткосрочный долг < 1,0; доля краткосрочного долга > 50%.
- Отрицательный капитал; EBITDA LTM ≤ 0; FCF отрицательный два периода подряд.
- Качественные (ищет LLM): существенная неопределённость в отношении непрерывности деятельности;
  реклассификация долгосрочного долга в краткосрочный из-за нарушения ковенантов;
  модифицированное мнение аудитора; смена аудитора.
Для банков и страховых — свои сигналы (определяются при добавлении таких компаний).
